## 二、经核实仍成立的建议（按优先级）

### P0 — 安全边界收口（评审共识：剩余主战场是"用错 API 也能破坏安全边界"）

1. **无界全表读兜底**（两份评审中唯一仍完全有效的 DoS 面）
   - 现状：显式分页有 100 行硬上限（`table_query/mod.rs:64`），但 `all()`/`select()` 不加分页时 `apply_db_plan` 不加任何 `LIMIT`（`table_query/plan.rs:141-150`）。
   - 建议：为无分页查询增加服务端默认上限（可配置、可显式豁免），或在 `BuiltApp` 层强制 select 类 action 必须走 `paginate()`。

2. **裸 SQL escape hatch 降权**
   - 现状：`query(&str)`/`execute(&str)`/`init()` 已 deprecated 但仍 `pub`（`crates/yang-db/src/mysql/database.rs:299-395`，postgres 同构）；`create_table` 甚至无 deprecated 标注。
   - 建议：下一 breaking release 将其移到独立 `raw-sql` feature 或降为 `pub(crate)`；初始化类接口（建表/脚本执行）与运行时查询 API 分离。

3. **移除或隔离 `parse_token_unsafe`**
   - 现状：`pub` + deprecated，关闭签名/exp/nbf/aud 校验（`crates/yang-base/src/token/manager.rs:665-678`）；当前仅测试使用，鉴权主链路不经过它。
   - 建议：改为 `decode_unverified_for_debug` 并移入 debug/test-only feature。

4. **GitHub Actions 供应链固定**
   - 现状：仅 `cargo-deny-action` 已 pin SHA；`checkout@v4`、`dtolnay/rust-toolchain@master`、`rust-cache@v2`、`upload-artifact@v7` 均为可变引用（`.github/workflows/ci.yml`）。
   - 建议：全部改为 full-length SHA + 注释版本号，并加 Dependabot/Renovate 跟踪更新。

### P1 — 校验深度与一致性补强

5. **nbf 校验缺口**：`build_validation` 未开启 nbf（jsonwebtoken 9.3.1 默认关闭），生成的 token 写入了 nbf 但验证不强制（`token/manager.rs:46-58`）。建议开启或明确文档化该取舍。
6. **旧构造器密钥强度不对齐**：32 字节最小 HMAC 密钥仅约束 keyring 路径，`new_symmetric` 不受限（`token/manager.rs:213-246`）。建议对齐或废弃旧构造器。
7. **时钟漂移零容差**：黑名单 TTL = exp − now 精确匹配、`leeway = 0`。单机自洽，多节点部署无缓冲。建议：为 TTL 与 leeway 增加小的可配置漂移窗口，或文档化"多节点部署需时钟同步"的前置条件。
8. **认证相关概念进一步类型化**（文档 2 建议，方向正确）：`AuthenticatedUser`、`VerifiedToken`、`TrustedClientIp`、`VerifiedOrigin` 等，让不可信值无法自然流入安全决策代码。沿用现有 `TenantAccess` 代数和类型的成功模式。

### P2 — 工程与文档 hygiene

9. **修复文档腐化**（本次核实新发现，两份评审均未提）：
   - `query_builder/builder.rs:12-18, 477, 488` 的 doc 仍描述旧 `&str` API（"接受 SQL 表达式"），签名早已改为 `&FieldRef`；
   - doc 引用了不存在的方法 `order_identifier`/`group_identifier`/`join_on_identifiers`；
   - `table_query/query_params.rs:261, 273` 与 `filters.rs:647, 687` 关于"空逻辑组等价 1=1/1=0"的 doc 与实际的拒绝行为不一致。
10. **yang-system best-effort 路径故障语义分级**（文档 2 建议，核实属实）：登录成功后会话记录/事件记录/新设备邮件目前仅 warn（`login.rs:193-205, 294-318`）。建议分类：安全事实必须阻断；审计事实进入 durable retry/outbox；业务增强允许 best-effort。
11. **建立对抗性集成测试套件**（文档 2 Phase 1）：SQL 注入变体、越权查询/排序/筛选、租户穿透、Refresh replay、revoked token race、Step-up proof replay、MFA 爆破、Host/Origin/Forwarded 伪造、schema migration race、shutdown/readiness race。现有测试证明"正常路径正确"，缺的是"安全不变量不可绕过"的专门证明。

### 暂缓 / 低优先

12. **CPU 密集操作隔离**：argon2id 等哈希运算调度至 `spawn_blocking`（文档 1 阶段三）。方向正确，但需先实测确认当前是否在线程池执行，再决定是否投入。
13. **Record 强类型化演进**（文档 1 阶段三）：用 derive 宏为业务表生成静态类型查询构建器。属长期演进，yang-system 侧可按需渐进，不宜作为基础库近期的破坏性变更。
14. **Release engineering 完整化**（文档 2 Phase 2：SBOM、provenance、镜像 digest、changelog 契约）：在 P0/P1 收口后推进。

## 三、核实确认的既有优势（保持，勿回退）

- 构建期冻结 + 运行期不可变（`AppBuilder` 10+ 项校验）；资源经 `ToolsBuilder` 显式所有权，无资源类全局单例。
- TableQuery 八项安全边界（权限、深度 32、LIKE 128、IN 500、空组拒绝、类型校验、标识符三层防护、分页上限）。
- JWT keyring：算法白名单、稳定 kid（缺失/未知即拒）、8 把密钥上限、签发/验证双侧 alg 比对。
- 撤销链路全路径 fail-close（含回归测试锁定）。
- yang-system：等时校验 + 防枚举、Cookie 三属性 + Same-Origin、config deny_unknown_fields + 脱敏 + secret 目录源、非 root 容器、带 readiness gate 与共享关闭预算的启动/停机序列。
