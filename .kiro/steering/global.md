# 全局规则

本规则适用于所有对话、代码编写和修改，每次交互都必须严格遵守。

## 语言要求

- 所有对话回答必须使用中文
- 所有代码注释必须使用中文
- 所有文档内容必须使用中文
- 所有变量名、函数名、类名等命名使用有意义的英文

## 命名规范

- 变量、函数、文件名：蛇形命名法（snake_case），例如 `connect_mysql`、`user_name`、`process_data`
- 结构体、枚举、trait：大驼峰命名法（PascalCase），例如 `UserConfig`、`DataSource`
- 常量：全大写蛇形（SCREAMING_SNAKE_CASE），例如 `MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT`
- 模块名：蛇形命名法（snake_case），例如 `level_graph`、`db_connection`
- 生命周期参数：小写单字母，例如 `'a`、`'b`
- 泛型参数：大写单字母或大驼峰，例如 `T`、`TResult`

## 代码质量要求

### 易读性
- 代码结构清晰，逻辑直观
- 避免过度复杂的表达式，适当拆分长函数
- 函数长度控制在 50 行以内（特殊情况除外）
- 使用有意义的变量名，避免单字母变量（循环索引除外）
- 合理使用空行分隔逻辑块

### 健壮性
- 添加必要的错误处理，使用 `Result` 和 `Option` 处理异常
- 考虑边界情况和异常输入
- 避免 `unwrap()` 和 `expect()`，除非有充分理由
- 使用 `?` 操作符简化错误传播
- 对外部输入进行验证

### 可拓展性
- 使用 trait 和泛型提高灵活性
- 设计时预留扩展点
- 避免硬编码，使用配置或参数
- 接口设计考虑向后兼容性

### 可维护性
- 模块化设计，单一职责原则
- 避免重复代码，提取公共逻辑
- 保持依赖关系清晰
- 定期重构，消除技术债务

## 代码规范

### 格式化
- 遵循 Rust 社区编码风格（rustfmt 标准）
- 使用 4 空格缩进
- 行宽限制在 100 字符以内
- 使用 `cargo fmt` 自动格式化

### 注释规范
- 公开 API 必须添加中文文档注释（`///`）
- 文档注释包含功能说明、参数说明、返回值说明、示例代码
- 复杂逻辑必须添加中文行内注释（`//`）
- 注释与代码保持同步更新

### 错误处理
- 错误类型需有清晰的中文描述
- 使用自定义错误类型，实现 `std::error::Error`
- 错误信息包含足够的上下文信息
- 考虑使用 `thiserror` 或 `anyhow` 简化错误处理

### 测试规范
- 关键功能必须编写单元测试
- 测试函数使用 `test_` 前缀，例如 `test_connect_mysql`
- 测试覆盖正常情况和边界情况
- 使用 `#[cfg(test)]` 模块组织测试代码
- 所有测试代码统一放到测试目标模块文件夹下的 `__test__` 文件夹中
- 每次测试只运行目标测试模块的指定测试代码，使用 `cargo test --test <测试文件名>` 或 `cargo test <测试函数名>`，不要全部测试代码一起运行，以提高测试效率

### 依赖管理
- 谨慎添加外部依赖
- 优先使用标准库
- 定期更新依赖版本
- 在 `Cargo.toml` 中添加依赖说明注释

## 项目背景

这是一个基于 Rust 的 YANG 相关项目，包含以下 crate：

- `yang-base`：YANG 基础库，提供核心数据结构和通用工具
- `yang-db`：YANG 数据库相关功能，负责数据持久化
- `yang-pcg`：YANG 配置生成器，负责配置的生成与管理

## 代码审查要点

在提交代码前，确保：
- 代码通过 `cargo check` 检查
- 代码通过 `cargo clippy` 检查
- 代码通过 `cargo fmt --check` 检查
- 所有测试通过 `cargo test`
- 文档生成正常 `cargo doc`
- 没有未使用的导入和变量
