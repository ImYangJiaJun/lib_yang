# yang-db 代码审查报告

- 审查日期：2026-06-02
- 审查范围：`crates/yang-db/src/` 全部 13 个源文件（MySQL 查询构建器 + Redis 客户端，约 11.6k 行）
- 方法：逐文件人工通读 + 多维度并行审查（安全 / 正确性 / 完善性 / 优化），每条发现均重读源码做对抗性核验，最终确认 72 条、驳回 9 条误报。
- 结论强度说明：标注"注入面"的条目，实际可利用性取决于下游（`yang-base`）是否把外部输入路由到标识符位置；`yang-base` 已用封闭的 `<Name>Field`/`<Name>Where` 枚举规避，故现状是"靠上层约定安全，而非靠构造安全"。

---

## 总体评价

最关键的一点是对的：**所有"值"都走 `?` 占位符 + `sqlx::bind` / `redis::cmd().arg()` 参数化**，覆盖查询构建器、`*_with_params` 原始路径、事务与每个 Redis 命令，无一例外。`value.rs` 覆盖了全部 `redis::Value` 变体且不 panic，Redis 连接池配置（`max_size` + wait/create/recycle 超时）确实接进了 deadpool，测试覆盖（含 property test）也较扎实。

问题集中在三块：**标识符拼接（注入面）**、**若干语义正确性 bug**、**错误建模脆弱**。下面按严重级别与主题归类。

## 一、安全

### 安全-1：`table_exists` 把表名拼进单引号字符串字面量（真值注入）— High

- 位置：`mysql/database.rs:184`
- 现状：
  ```rust
  let sql = format!(
      "SELECT COUNT(*) as count FROM information_schema.tables \
       WHERE table_schema = DATABASE() AND table_name = '{}'",
      table_name
  );
  ```
- 问题：表名被拼进**单引号字符串字面量**，这是经典的值注入，而非标识符问题，且与全库"值一律参数化"的约定直接冲突。
- 修复（成本最低，应最先做）：
  ```rust
  let sql = "SELECT COUNT(*) as count FROM information_schema.tables \
             WHERE table_schema = DATABASE() AND table_name = ?";
  let row: (i64,) = sqlx::query_as(sql).bind(table_name).fetch_one(&self.pool).await?;
  ```
- 相关次要项：`drop_table:177` 用反引号包裹表名但未转义内部反引号，属同类（标识符未转义）。

### 安全-2：标识符（表名/列名/字段/JOIN）全程裸拼接，无白名单无转义 — High

- 根因：`SqlGenerator::append`（`query_builder.rs:88-90`）仅 `push_str`，无任何转义；所有标识符经 `format!`/`push_str` 原样进 SQL，只有"值"走 `?`。
- 精确落点：
  - `condition.rs:140-187`（借用版）与 `233-281`（owned 版）：`format!("{} = ?", field)` 等全部比较变体，列名裸拼。
  - `query_builder.rs`：
    - `build_select`：SELECT 字段 `:145`、FROM 表名 `:150`
    - `build_order_by:258`：`format!("{} {}", order.field, direction)`（方向由 `bool` 决定，不可注入；仅 `field` 可注入）
    - `build_group_by:275`
    - `build_insert:339-341` / `build_insert_batch:390-392` / `build_update:471-478` / `build_delete:517` / `build_update_batch:562-604` / `build_upsert:647-666`：表名与**列名（取自 JSON 对象 key）**裸拼
    - 聚合 `sum/avg/min/max`：如 `:1605` `format!("CAST(SUM({}) AS DOUBLE)", field)`
  - `build_joins:226-240` + `join/left_join/right_join:1161-1194`：`table` 裸拼，`on` 是**整段自由 SQL**，结构上连内嵌值都无法参数化——注入面最大。
  - 事务路径 `transaction.rs`：`TransactionQueryBuilder` 的表名/列名/字段名同样裸拼。
- 准确性说明：`yang-base` 用封闭字段枚举挡住了外部输入当列名，但 `yang-db` 库层零防御；且 INSERT/UPDATE 列名直接来自 `serde_json` 对象 key，任何把不可信 JSON 当行数据喂进来的下游都会把攻击者控制的 key 变成裸 SQL 标识符。
- 修复：在 `SqlGenerator`/`QueryBuilder` 内提供单一 `quote_ident()` 入口：
  - 白名单校验 `^[A-Za-z_][A-Za-z0-9_]*$`（允许 `schema.table.col` 按点拆分逐段校验），非法名返回 `DbError`（沿用 `UnsupportedOperator` 的错误风格）；或
  - 反引号包裹并对内部 `` ` `` 双写转义。
  - 所有 `build_*` 强制走它；表名在 `QueryBuilder::new` 处即校验。
  - 对 `join` 提供结构化 API（左列/操作符/右列分别传入校验），或显式标注 `_unchecked` 语义、仅接受可信常量。
  - 提供 checked / `_unchecked` 双轨，与现有 `where_and`/`where_and_unchecked` 约定一致。
  - 补 proptest：含特殊字符的列名/表名要么被拒、要么被正确转义。
- 注意：`query_builder.rs` 4.8k 行、耦合高，AGENTS.md 要求拆改配测。

### 安全-3：信息泄漏 — Medium

- `redis/client.rs:110`：启用日志时把**完整 Redis URL 打进 info 日志**，含明文密码。应脱敏后再记（如只记 host:port/db）。
- `error.rs`：数据库原始 `message`/`Display` 直接透传进错误，可能带出数据值与查询片段。

## 二、正确性

### 正确性-1：Redis 乐观锁事务根本性损坏 — High

位置：`redis/transaction.rs`（`exec` / `execute`，`:292-371`，冲突判断 `:325`）

四个叠加问题：

1. **冲突被静默吞掉**：WATCH 冲突时 EXEC 返回 nil，靠 `err_msg.contains("EXECABORT") || err_msg.contains("nil")` 判断。`execute()`（走 `exec::<Vec<_>>`）与 `exec::<()>` 等路径下，nil 不一定以可被 `contains("nil")` 命中的错误形式出现，自动重试形同虚设。
2. **重试只重放固定 pipe**：冲突后无法重新读取被监视键并重算，这不是真正的 CAS——pipe 在 `new()` 时已 `.atomic()` 且命令固定，重放结果不变。
3. **不清理 WATCH**：提前返回（非冲突错误）时不 `UNWATCH`/`DISCARD`，连接带着悬挂的 WATCH 归还连接池，污染后续使用者。
4. **重试无退避**：`MAX_RETRIES = 100` 紧凑空转，冲突时猛击 Redis。

建议：重新设计为闭包式事务 `tx(|conn| async { 读→算→MULTI→EXEC })`，由框架负责 WATCH、冲突重试（带退避）与连接清理；而非固定 pipe 重放。

### 正确性-2：Pipeline / 事务多值命令返回值错位 — Medium（真 bug）

位置：`redis/pipeline.rs`（`lpush/rpush/sadd/zadd`，`:171-225`）与 `redis/transaction.rs`（同名方法 `:195-249`）

```rust
pub fn lpush(&mut self, key: impl Into<String>, values: &[String]) -> &mut Self {
    let key_str = key.into();
    for value in values { self.pipe.lpush(&key_str, value); }  // N 条命令，不是 1 条
    self
}
```

调用方以为加了一条命令，实际结果向量里出现 N 个返回值，破坏"按添加顺序对齐结果"的契约。应改用变长参数一次性 `LPUSH key v1 v2 ...`（`self.pipe.lpush(&key_str, values)`）。

### 正确性-3：批量写入静默丢数据 — Medium

- `build_insert_batch`（`:386`）：字段名只取**首条记录**的 key，后续记录多余字段被静默丢弃、缺失字段静默填 NULL。
- `build_update_batch`（`:580-604`）：不校验记录含 `id_field`，缺失时生成 `WHEN id=NULL` / `IN (NULL)`，**静默零命中**。

建议：强制所有记录字段一致并校验，或在文档明确该行为。

### 正确性-4：数值精度 — Medium / Low

- `database.rs` `bind_json_param` / `bind_json_param_as`（`:302-311` 等）：超出 i64 范围的大整数退化为 **f64 字符串**，精度丢失。
- `condition.rs` `From<u64> for SqlValue`（`:62`）：`as i64`，超过 `i64::MAX` 时静默回绕（雪花 ID 通常在 i64 内，但 API 仍不安全）。

### 正确性-5：错误建模脆弱 — Medium

- `error.rs:104` `From<redis::RedisError>`：用 `to_string().contains("...")` 判错误类型，大小写 / i18n / 措辞变化即误判。应改用 `err.kind()` 结构化判别。
- `error.rs:62` `From<sqlx::Error>`：错误码映射不全——**死锁 1213、锁等待超时 1205** 未识别，且 `TransactionError` 变体实际**从不产生**（无路径构造）。

### 正确性-6：其他正确性 — Low

- `count()` / `value()` 与 GROUP BY 组合时被自动 `LIMIT 1` 截断，只返回首个分组结果。
- `to_sql()`（`:1229`）生成失败时**静默回退**成残缺 SQL（丢 WHERE/JOIN/GROUP/HAVING/ORDER/LIMIT），调试误导。
- `where_and`/`where_or` 的 `like` 操作符对非字符串值用 `{:?}` Debug 格式当匹配模式（`:904`/`:964`），产生错误语义。
- `parse_scan_result`（`:2023`）/ SCAN 游标用 i64（Redis 是 u64），异常响应被当成"迭代完成"返回 `(0, vec![])`；大 keyspace 下可能提前终止、静默漏键。
- `health_check` 吞掉所有错误返回 `Ok(false)`，与文档"无法获取连接返回 Err"契约不符。
- `del/exists` 等多键命令对空切片不校验，触发 Redis 端 "wrong number of arguments"。
- `init()`（`database.rs:154`）按 `;` 粗暴切分 SQL，字符串内分号会切错语句，且非事务。
- LIKE 模式未转义 `%`/`_` 通配符，也无文档说明。
- `From<redis::Value>` 未处理 `ServerError` 变体，数组内逐元素服务端错误被转成字符串掩盖；`Set/Map/VerbatimString` 用 Debug 文本化，RESP3 下 SMEMBERS 等受影响。

## 三、完善性

- **`TransactionQueryBuilder` 能力严重缺失 — Medium**（`transaction.rs:200-498`）：只有 `where_and`，缺 OR / IN / BETWEEN / NULL，也没有 batch / upsert / select。事务里能做的远少于普通 `QueryBuilder`，API 不对称。
- **无语句级超时 — Medium**：MySQL 查询与 Redis 命令都没有单次操作超时，慢查询 / 卡连接无上限。建议提供按操作的 timeout。
- **pub/sub 仅实现 PUBLISH**：缺 SUBSCRIBE/PSUBSCRIBE，与 AGENTS.md 宣称的 "pubsub" 能力不符。
- **KEYS 作为公开 API 暴露**（`client.rs:1747`）：阻塞风险；已提供 SCAN 替代，但 `yang-base` 包装层 `GlobalRedis::keys` 丢弃了阻塞风险警告。
- **MySQL 侧缺 `health_check` / `pool_status`**：与 Redis 侧不对称，可观测性缺口。
- **`DatabaseConfig.connect_timeout` 实际映射到 `acquire_timeout`**（`database.rs:100`）：连接池取连接超时，而非 TCP 连接超时，命名误导；缺 `min_connections` / `max_lifetime`。
- **`where_*_unchecked` 会 panic 但未标注 deprecated**：与 `having_cond_unchecked` 处理不一致。

## 四、可优化 / 可简化（收益主要是可维护性，非 bug）

值得做的去重：

- `insert_batch` 直接委托 `insert_batch_with_size`，并停止每批重建整个 `QueryBuilder`（clone 多余）。
- `sum/avg/min/max/value` 五个方法大段样板 → 抽公共标量查询助手。
- `condition_to_sql` 与 `condition_to_sql_owned` 近乎整体重复；且 `build_where` 走借用版导致双重 clone。
- `bind_json_param` 与 `bind_json_param_as`（`database.rs`）、`where_and`/`where_or`/`having_cond` 的 `op→Condition` 匹配，均为重复逻辑。
- Redis 客户端大量重复 `.as_i64().ok_or_else(整数错误)` 与 `as_array→filter_map` 收集样板，可抽助手。
- `RedisValue` 访问器一律 clone，列表类读命令对自有数组逐项克隆；`BulkString` UTF-8 转换前多余 clone 整段字节。
- `build_order_by`/`build_having` 多条件分支先收集 `Vec<String>` 再 join，可直接写入 `self.sql`（与文件内已优化的 `push_str` 风格一致）。

可清理的死代码 / 陈旧物：

- `RedisConfig::{connect,wait}_timeout_duration` 与 `RedisClient.config` 字段实际未读取（dead_code），client 内重复手搓 Duration。
- 注释写 "redis 1.1.0"，实际依赖 1.2.0。
- 事务里 "事务已提交或回滚" 分支为不可达死代码。
- `build_select`/`build_upsert` 用 `format!+append`，与文件内 `push_str` 风格不一致。
- nit：`Okay→Bool(true)` 与 `SimpleString("OK")→String("OK")` 不一致。
- owned/borrowed 等价性 property test 只校验参数个数，未校验参数值与顺序。

## 五、被驳回的误报（9 条）

对抗性核验阶段驳回，不应作为修复项：

- 把"既定约定"当新问题：值参数化本身、`_unchecked` 按设计 panic 属预期行为。
- `RedisConfig` 池参数"未生效"的旧说法——`connect_with_config` 已正确接入 deadpool（`max_size` + wait/create/recycle 超时），AGENTS.md 反模式条目成立。
- 部分行号定位不准或与实际实现不符的条目。

## 六、建议修复顺序（按 风险÷成本）

1. **`table_exists` 参数化**（约 5 分钟，消除真值注入）— 安全-1
2. **Pipeline / 事务多值命令返回值错位**（真 bug，影响正确性）— 正确性-2
3. **`error.rs` 改用 `err.kind()` + 补 1213/1205 错误码**— 正确性-5
4. **统一 `quote_ident()` 标识符校验层**（覆盖全部 `build_*`，配 proptest；改动 4.8k 行的 `query_builder.rs`，需配套测试）— 安全-2
5. **重做 Redis 乐观锁事务**（闭包式 + UNWATCH + 退避）— 正确性-1
6. 批量写入字段校验、大整数精度、语句级超时、`TransactionQueryBuilder` 补齐 — 正确性-3/4、完善性

每项修复后运行：

```bash
cargo test --lib -p yang-db
cargo test --test <name> -- --ignored --test-threads=1   # 需要 Docker 的集成测试
```

第 1–3 项低风险高收益，可独立提交；第 4、5 项改动面大、涉及事务语义与 `query_builder.rs`，建议各自单独配测试后再改。
